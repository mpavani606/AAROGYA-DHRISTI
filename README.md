# Aarogya Drishti

Synthetic hackathon simulation for the ITDA Paderu area. **NOT FOR CLINICAL USE.**

## Demo accounts

Run `npm run seed -w server` with MongoDB available. The seed includes synthetic ASHA worker, doctor, district-admin, system-admin, and patient accounts (no Employee accounts), plus explicitly fictional demo booking facilities and clinicians for all 11 seeded Alluri mandals. Their weekday appointment schedules are generated for the next two weeks and refreshed without overwriting existing bookings. Demo records are not a real facility or clinician directory and must never be used for care. The seeded accounts use:

- Password: `Demo12345!`
- Email format: `asha.demo@demo.local`, `mo.demo@demo.local`, `specialist.demo@demo.local`, `district.demo@demo.local`, `admin.demo@demo.local`, `patient.demo@demo.local`
- Additional fictional clinician accounts: `doctor.asr.03.demo@demo.local` through `doctor.asr.11.demo@demo.local`
- ASHA worker sign-in requires MFA enrollment on first login; local development displays a short-lived demo TOTP code during setup.

Legacy Employee records are retained in MongoDB but cannot sign in, refresh sessions, or access protected APIs; the seed no longer creates Employee accounts. For local development, `.env.example` uses `SMS_MODE=mock`; OTP requests return a development code for local testing only. Production requires `SMS_MODE=live` and the Twilio account SID, auth token, and sender number in `.env`, and does not provide a fallback code. Patient OTP sign-in is available at `/patient/login` for phone numbers linked to an active patient record.

## Patient and doctor onboarding (Phase 06)

First-time visitors must choose English, Telugu, or Hindi before the main application home opens. The selected language is applied across the app and can be changed later. The home page provides separate Patient and Doctor sign-in links; each role's registration is offered from its own sign-in page. Patient sign-in is at `/patient/login`, registration is at `/patient/register`, Doctor sign-in is at `/doctor/login`, and registration is at `/doctor/register`. Doctors can sign in using their registered email, username, or mobile number and bcrypt-verified password, then must enroll authenticator TOTP on first sign-in and enter a TOTP code on subsequent sign-ins before a session is issued. Patient records remain pending until the existing mobile OTP flow verifies the number. Registration consent is recorded, and a patient account becomes available only after successful OTP verification. Local development can use mock patient OTP as described above; production requires the live SMS provider and has no development-OTP fallback.

Doctor registration is available at `/doctor/register` and collects the doctor's name, unique username, email and mobile, professional registration number and authority, specialty, hospital name, qualification, experience, and password with confirmation. Passwords are bcrypt-hashed. MongoDB uniqueness constraints prevent duplicate emails, usernames, mobile numbers, and professional registration numbers; duplicate responses identify the conflicting field without exposing account details. Successful registrations are not capped by an account-count limit. New profiles remain unverified and must complete the professional verification workflow. Doctors upload documents from the authenticated profile at `/doctor/profile`; `type` is one of `registration_certificate`, `qualification`, `experience_certificate`, `identity`, or `other`. Every multipart upload includes `file` and a UUID `uploadId` for safe retries. At least one separate registration certificate and one qualification document are required to submit; supporting documents can be uploaded multiple times. Files are limited to PDF/JPG/PNG and 10 MB, validated by extension and content signature, and remain `uploaded` until submission changes them to `pending`. Only a System Admin can review the profile; approved and rejected document statuses, review remarks, and verification dates are retained.

Patient screening is available after sign-in and requires a separate screening-consent acknowledgement. The existing patient case workflow resolves the patient's own linked record; patient case creation and screening endpoints enforce ownership and active consent on the server. Screening is a non-clinical simulation, not a diagnosis.

## Screening, referrals, and follow-up (Phase 07)

Screening reuses the existing deterministic demonstration model and does not provide a diagnosis or clinically validated result. Patients can view their own care summary, appointments, referrals, and follow-up status. Verified doctors can independently review cases, request image recapture, create referrals to active hospitals, accept eligible referrals, assign follow-ups, and download an authorized synthetic care report. Doctor case summaries and case images are limited to the authorized case; patient-level reports and summaries use the existing care-relationship checks.

Newly uploaded screening images are encrypted in local storage and are served only through authenticated, consent-gated case routes. Older image files remain readable in their existing storage format. Screening consent is required for case creation and image/AI processing. In-app workflow notifications are queued with event deduplication; SMS/push delivery is not claimed. Reports are generated on demand, contain a non-clinical disclaimer, and access is audited. AI and all screening flows remain synthetic and are not for clinical use.

The patient oral-screening flow supports capture or upload for the tongue, gums, inner cheek, lips, palate, floor of mouth, and other oral areas. When the patient has separately consented to external AI, the configured Gemini provider may return an unvalidated visual description and image-quality label; otherwise the local deterministic demonstration makes no clinical image assessment. The case-level screening PDF includes the uploaded image, available observation and quality metadata, reported symptoms, limitations, and general professional-care guidance. Image-based disease identification and Low/Medium/High risk classification are intentionally not provided: no configured model is clinically validated for those decisions. The PDF explicitly distinguishes preliminary screening from diagnosis and recommends qualified clinician review.

Run the backend unit/API tests with `npm test -w server`; these do not require MongoDB. The Phase 07 MongoDB workflow tests are opt-in via `RUN_PHASE7_MONGO_INTEGRATION_TESTS=1` and require `MONGODB_URI` to point to a loopback-only database named `aarogya_phase07_<unique suffix>`. The suite drops only that explicitly named test database before and after the run. Never point it at production or user data.

Run the browser workflow suite with `npm run test:e2e -w client -- --workers=1`. It uses synthetic API responses and validates the client workflows and API contracts; it does not replace the isolated MongoDB integration tests.

## Patient dashboard

The patient-only `/patient-dashboard` route presents 11 sections, including My ASHA / Health Worker and Health Camps, using patient profile, screening, appointment, Daily video, AAROHINI, records, emergency, notification, consent, community, and encrypted offline-sync services. Patient profile edits, prescriptions, and medication refill requests use token-derived patient identity; refill requests can be queued offline. SOS requests can also be queued offline and are explicitly marked as not yet received until synchronization. Appointment requests are checked against the live doctor schedule; offline appointment submission is queued for slot revalidation on synchronization and may fail if the slot has since been taken.

Medicine availability is sourced from stock entered by hospital managers for their assigned hospital. Patients can search their own district's active hospitals; an unrecorded medicine is explicitly not represented as out of stock, and patients should call to confirm before travelling. Prescription records are patient-scoped; patient-entered items are labelled patient-reported and do not create or alter a clinician's prescription. Refill requests link only to that patient's prescription or medical record and create an in-app notification. The existing deterministic screening remains available. A patient may separately opt in to an external Gemini visual observation in dashboard privacy settings. When `GEMINI_API_KEY` is configured, consented images are sent from the server to Google Gemini; the server key is never sent to the browser. The feature returns only an unvalidated visual description and image-quality label, not a diagnosis, cancer-risk estimate, or treatment recommendation, and requires independent clinician review. Obtain organizational/privacy approval before enabling the provider for real patient data. Without explicit consent or a configured key, no image is sent to Gemini. Daily video rooms require server-side `DAILY_API_KEY`; audio-only use is available by turning off the camera in the Daily room. Dashboard labels are available in English and Telugu.

## Operational analytics and monitoring (Phase 08)

The protected `/analytics` page provides aggregate screening, review, referral, follow-up, appointment, staffing, and monthly-trend metrics. Users can filter by date and status; district and system administrators can also select mandals, and System Admin can select a hospital. Server-side scope checks run before query filters: district administrators are restricted to assigned geography, Hospital Managers to their active assigned hospital, and doctors to records covered by their own assignment or appointment relationship. Patient names, phone numbers, images, and case-level details are not included in analytics or exports.

System Admin additionally has access to `/api/v1/ai-monitoring` and `/api/v1/system-health`. AI operational events store aggregate status, duration, model version, and a fixed error code only. The reported AI is the current local deterministic demonstration; metrics do not indicate clinical performance, and outputs are not validated diagnoses. Detailed health covers this API process, database ping, media-storage configuration/availability, notification queue counts, and registered background jobs. Request and job counters are in-process and restart with the API; they are not a distributed monitoring system. Cloud storage configuration is reported as configured but unverified; this endpoint does not claim a provider health check.

Authorized aggregate reports are available as CSV or PDF from the analytics page and are audited. They contain a non-clinical simulation disclaimer. No patient-level reports are included in Phase 08 analytics exports. Phase 08's disposable MongoDB integration tests are opt-in via `RUN_PHASE8_MONGO_INTEGRATION_TESTS=1` and require a loopback-only `MONGODB_URI` whose database is uniquely named `aarogya_phase08_<unique suffix>`. The test drops only that explicitly named database during setup and teardown; never point it at production or user data.

## Clinical decision support and AAROHINI voice (Phase 09)

Verified doctors can open `GET /api/v1/cases/{id}/clinical-summary` for an audited, no-store structured summary when they have an authorized case-care relationship and the patient has active screening consent. It presents recorded case notes, patient-level symptoms and habits (the reporter is not captured and they are explicitly marked as not linked to the specific case), stored rule-based indicators, image quality history, and the latest doctor assessment.

This endpoint is a factual record summary, not an AI-generated assessment. It explicitly returns `NO_VALIDATED_CLINICAL_MODEL` and does not send patient records to an external generative AI provider. The currently available image model remains a deterministic demonstration with no clinical validation; no diagnostic accuracy is claimed. Doctors retain control of assessments, referrals, and follow-ups through the existing workflows.

The existing multilingual education and registration assistant is branded AAROHINI in the UI and retains its secured OpenAI Realtime/WebRTC voice and reviewed-knowledge tool when provider configuration is present. It is not a clinical assistant and must not receive patient identifiers. The app's current notification workflow queues in-app messages only; SMS/push provider delivery is not configured or claimed. No new AI provider or database integration was added for this phase.

## Hospital, doctor, and patient workflows

The admin dashboard is protected; an authorized district or system administrator must sign in before accessing it. Admin operations support hospital creation, search, editing, and activation/deactivation, plus doctor account lookup. Doctors authenticate with their registered email and password, enroll in authenticator TOTP, complete a professional profile, upload distinct registration, qualification, experience, identity, and supporting documents, and submit for System Admin verification. All privileged roles must complete MFA before accessing protected features. Verification is not automatic; unverified doctors cannot use clinical workflows. System Admins can review evidence, suspend verification, and disable accounts; Hospital Managers can see only their assigned hospital's doctor verification status and cannot approve credentials. Rejection remarks are shown to the doctor, who can replace rejected documents and resubmit. Professional files use the existing private storage and encryption mechanisms.

Hospital records include district/mandal, a separate Government/Private classification, contact details, and assigned/active doctor totals. New hospitals can be associated with the seeded Alluri Sitharama Raju district and its mandals; real facility and doctor data must be entered by an authorized administrator. The seed-created demo entries are marked synthetic and the appointment page warns patients not to rely on them.

The existing `/appointments#hospital-directory` section now reads the ASR public directory from MongoDB through the authenticated `/api/v1/facility-directory` API. Import or refresh it with `npm run seed -w server` or `npm run seed:directory -w server` (directory updates are idempotent), or run the focused importer from the `server` workspace with `npx tsx src/seed/asrDirectory.ts`. The source contains 62 PHCs and four major facilities; the application excludes Addateegala, Chintapalli, Chintur, Devipatnam, Gangavaram, Kunavaram, Maredumilli, Nellipaka, Rajavommangi, Rampachodavaram, Vararamchandrapuram, and Y. Ramavaram, leaving 31 PHCs, 31 linked Medical Officer/contact-person records, and three major facilities across the other 10 mandals. The source spellings `Chintapalle` and `Vararamachandrapuram` are treated as the requested Chintapalli and Vararamchandrapuram. The source is the APMSIDC tender snapshot dated 10 July 2023, plus major-facility details verified on the ASR District Administration health page. Source and import dates are shown in the UI. The source does not supply PHC facility codes, street addresses, facility contacts, specialties, medical registration numbers, or HPR IDs; those fields remain unavailable. The PDF snapshot is historical and not independently verified for current postings. These directory contacts are informational only and are not bookable doctors; appointment booking continues to use only the existing active, verified clinician workflow. Directory imports use separate collections and do not overwrite existing Hospital, User, or DoctorProfile records.

Patient mobile OTP sign-in uses the live SMS provider and only issues patient access for a unique active patient record with a matching verified phone. Existing patient records must contain a phone number. Patient record uploads accept PDF/JPG/PNG files up to 10 MB and can retain the record date, hospital name and ownership, previous treating doctor's name, treatment details, and uploaded files. Files are stored in configured private Cloudinary storage or private local storage. Local files are encrypted with AES-GCM using `APP_ENCRYPTION_KEY`; Cloudinary files use private storage and short-lived signed links. Patient and assigned-care-team access is protected by server-side care-relationship checks; file links expire after five minutes. Configure Cloudinary credentials for managed private storage, or keep local storage on a persistent, access-controlled server volume.

Patient appointment requests use exact future schedule windows entered by a hospital manager; an appointment cannot be created for an unlisted or already-reserved time. The weekday, date, and consultation hours are shown before booking. Confirmed video appointments create private Daily.co rooms and short-lived participant tokens. Set `DAILY_API_KEY` in the server environment before enabling video calls; it must never be exposed in client configuration. Recording is disabled and rooms expire with the appointment. Daily.co is an external processor, so obtain the required organizational/privacy approval before using it for real consultations.

## Manual offline sync demo

1. Start MongoDB, then run `npm run dev`. Sign in as a doctor only after the account has completed MFA and System Admin verification. Employee accounts are no longer active.
2. Register a synthetic patient while online once. Open `/sync` after sync completes, then use the patient/case flow available to the verified doctor. Set an offline PIN so captured images can be encrypted locally.
3. Open browser DevTools, select **Network → Offline** (or enable airplane mode), then save the patient/case draft. Confirm the bottom sync chip reports that data is saved locally and that no API request succeeds.
4. Open `/sync` while offline. Confirm the items appear under Pending. For an image case, keep the page open until its local encrypted image is queued.
5. Restore the network. The automatic sync should send operations in order; reopen `/sync` to see status. Repeating Sync should not create a duplicate record.
6. To exercise interrupted image uploads, set DevTools Offline after a few chunk requests, restore connectivity, and press Retry/Sync. The server reports received chunk indexes and the client sends only missing chunks.

Offline images are AES-GCM encrypted with a key derived from the user's local PIN (PBKDF2). The key stays in memory and auto-locks after five minutes of inactivity. Successfully uploaded local image blobs are retained for seven days, then purged. Workbox precaches the app shell, bundled locale/font assets and offline education JSON; audio files under `client/public/education/audio/` and generated audio responses are cached when played online.

## Community health coordination (Phase 10)

The protected `/community` portal adds health-camp scheduling, scoped camp status management, registration of existing patient records, attendance recording, and audited aggregate CSV reports. Camp creation validates that the selected village and PHC match the mandal; assigned doctors must be active and professionally verified. Patient participation and attendance require active screening consent. Reports omit patient-level data and suppress counts from one to four.

The same portal adds patient SOS request submission and a role/geography-scoped coordination queue. SOS requests are idempotent and attach a location only when the patient has active location consent and explicitly selects location sharing for that request. Facility distances are calculated only from an existing, consented location; open/closed status uses recorded weekly working hours, and is unknown when hours are not available. The portal does not dispatch emergency services, guarantee a response, or replace local emergency numbers. Notification assignment is in-app only.

Patient prescriptions, refills, SOS requests, and profile edits are persisted in MongoDB. Screening notifications are deduplicated per event and patient, and marking a notification read updates its stored status. Patient profile, refill, and SOS changes can be queued in the encrypted offline outbox; Sync now reports remaining items instead of claiming success when an operation is still pending. The 104 support link opens the phone dialer. Mongoose creates the prescription collection and indexes on first use; no separate database migration is required. Running `npm run seed -w server` adds clearly marked synthetic sample medicine stock only when the inventory collection is empty. Do not run the seed against an unverified database.

The doctor **Medicines & Prescriptions** page is available at `/doctor/prescriptions`. Running the standard seed also upserts 100 fictional demo prescriptions and their synthetic medicine catalog entries, linked to the existing synthetic patients and verified demo doctors. The seed can be rerun without creating duplicates. Dashboard search, filters, details, status statistics, and demo PDF downloads read from MongoDB. Demo prescriptions are labeled throughout, excluded from patient prescription history and refill selection, and cannot be approved, edited, or deleted as clinical records. Prescription and medicine APIs require a verified doctor; prescription access remains limited to assigned patients.

Existing follow-up scheduling, missed-appointment tasks, referral status, reviewed multilingual education/audio, hospital and diagnostic facility directory, aggregate village/PHC dashboards, contact attempts, and encrypted image sync are reused rather than duplicated.

The active `asha_worker` role uses the protected `/asha` dashboard and assigned-geography checks; public registration cannot assign this role. Legacy Employee accounts remain disabled. The `/community` portal and `/admin/dashboard/asha` views remain separately scoped to their authorized roles. Offline actions use the existing encrypted outbox and PIN-based local data protection; use synthetic records for demonstrations and verify the configured storage and key management before any real-data deployment.

Phase 10 integration tests are opt-in via `RUN_PHASE10_MONGO_INTEGRATION_TESTS=1` and require `MONGODB_URI` to reference a uniquely named loopback-only `aarogya_phase10_<unique suffix>` database. The suite drops only that explicitly named database during setup and teardown; never point it at production or user data.

## Oral health educational assistant (Phase 11)

Set server-only `OPENAI_API_KEY`, `OPENAI_REALTIME_MODEL`, `OPENAI_CHAT_MODEL`, `OPENAI_EMBEDDING_MODEL`, `RAG_VECTOR_INDEX`, and `RAG_MIN_SCORE`. Create an Atlas Vector Search index on the Mongoose `knowledgechunks` collection using the following JSON (index name must match `RAG_VECTOR_INDEX`; `text-embedding-3-small` produces 1536 dimensions):

```json
{
  "fields": [
    { "type": "vector", "path": "embedding", "numDimensions": 1536, "similarity": "cosine" },
    { "type": "filter", "path": "language" }
  ]
}
```

Only education articles with `reviewed` or `published` status and a clinician reviewer are ingested. After clinician review or content updates, run `npm run rag:ingest -w server`; removed/unreviewed pages are removed from the knowledge collection. Search returns at most `RAG_TOP_K` passages and returns an empty list when the best vector score is below `RAG_MIN_SCORE`. This requires MongoDB Atlas Vector Search; it does not silently substitute an ungrounded text search.

Authenticated endpoints: `POST /api/v1/rag/search`, `POST /api/v1/ai/tool/search_medical_knowledge`, `POST /api/v1/ai/chat`, and `POST /api/v1/ai/realtime/session`. Realtime creates a short-lived secret server-side and returns only `{ clientSecret, expiresAt }`; the long-lived API key never reaches the browser. The browser connects to OpenAI using WebRTC and executes the knowledge tool through the authenticated app API. The text endpoint applies the same prompt and retrieves reviewed passages before generating an answer. Each prompt/source/model/language record is stored without account or patient IDs; common phone, email, ABHA and self-labelled identity values are redacted. Exchange logs expire after 90 days. Never enter patient identifiers into the assistant.

The floating assistant supports education and registration-helper context, voice captions, text fallback and a pulsing 3D avatar. Microphone access requires browser permission and a secure context (HTTPS or localhost). If voice or OpenAI configuration is unavailable, use text; if reviewed RAG content is unavailable, the assistant says it does not know rather than answering from model memory.

## District dashboard (Phase 12)

District and system administrators can open `/admin/dashboard`. The dashboard API is role-gated and returns aggregate values only; CSV export is aggregate-only and writes an audit log. District-admin mandal access is restricted to their configured district/mandal assignments. Village counts below five are returned as `<5`. Map markers are shown only when explicit coordinates exist in the synthetic `Village` records; the dashboard does not estimate locations.

Dashboard endpoints are `GET /api/v1/dashboard/summary`, `/hotspots`, `/village-coverage`, `/data-quality`, `/asha/:id`, and `/export`. Filters `mandalId`, `phcId`, `villageId`, `from`, and `to` are supported. Screening coverage uses registered active patients aged 18+ as its denominator and therefore does not estimate unregistered residents. Date of birth is encrypted; age is derived for aggregate eligibility. Image usability is based on the stored image quality check. Server-side pending sync duration is unavailable because the current sync schema records completed operations only, and is reported as unavailable rather than zero. Village coverage uses the synthetic `Habitation.coverage` field (`>0` indicates coverage recorded; `0` indicates no coverage recorded), not patient-level counts. Add village/PHC/mandal references during registration for more complete aggregates. Existing encrypted phone values are not queried; a SHA-256 phone hash is used internally for duplicate-group counts and is excluded from patient API responses.

Run dashboard tests and builds with `npm test -w server` and `npm run build -w client`.

## Local stack and deployment

The local Compose stack starts MongoDB, seeds the synthetic demo records, then starts the API and Vite client:

1. Copy `.env.example` to `.env` and replace `JWT_SECRET`, `JWT_REFRESH_SECRET`, and `APP_ENCRYPTION_KEY` with independent random values of at least 32 characters. Keep `.env` private and never commit it.
2. Run `docker compose up --build`.
3. Open `http://localhost:5173`; the API health endpoint is `http://localhost:4000/api/v1/health`, and Swagger UI is at `http://localhost:4000/api-docs`.

To enable Gemini visual observations, add your Google AI Studio key to `GEMINI_API_KEY` in the project-root `.env` and restart the API. Keep the key server-side; never add it to a `VITE_*` setting or commit it. Patients must separately enable external-AI consent in dashboard privacy settings. Gemini analysis runs after an image is submitted, and its output is an unvalidated observation that requires clinician review—not a diagnosis.

In development, the API accepts loopback Vite origins on ports 5173–5199 (including Vite's automatic fallback ports); remote origins remain disallowed. The local stack uses synthetic data and an unauthenticated development-only MongoDB. For the TLS-terminated, authenticated production-like stack, configure the required MongoDB, secret, `CLIENT_URL`, and `TLS_CERT_DIR` values in `.env`, then run `docker compose -f docker-compose.prod.yml up --build -d`. Both Compose files seed demo records before the API starts.

The client uses the same-origin `/api/v1` path. Vite proxies `/api/` to the local backend during development, including when a browser reaches the dev server from another device; production Nginx also proxies `/api/` to the backend. Set the build-time `VITE_API_URL` only when the API is hosted on a different origin.

The production API trusts the single Nginx proxy hop configured in `deploy/nginx.conf` so IP-based limits use the client address. The general API limit is 600 requests per minute; stricter limits remain on authentication, registration, uploads, synchronization, AI, and emergency endpoints.

See [the architecture overview](./docs/ARCHITECTURE.md) for component boundaries and trust boundaries. Stop the local stack with `docker compose down`; persistent synthetic data is retained in named volumes.
